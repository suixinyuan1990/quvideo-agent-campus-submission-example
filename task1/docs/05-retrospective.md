# 回顾

## 最难的地方

难在同时满足三件容易互相打架的事。

第一，执行器不能先写死“读取、检查、查询、保存”。如果工具结果不影响下一步，冲突、补查和阻断就只是日志。现在的循环每次都把新观察交回决策函数。M10 和 M01 在查询之前可以走相同的前两步，查询结果一变，保存参数就变成承诺原时段或待确认的替代时段。

第二，不能靠自动重试冒充决策。规则超时是否再查一次，要看这次返回里的 `retryable`。M11 补查后仍然失败，于是停止；M12 补查成功，于是继续排期。不可重试的错误即使配置了多次失败，也只会调用一次。

第三，模型不能自己宣布发布或保存成功。保存状态从工具观察汇总，发布状态没有写入途径。用户确认也放在原始请求里，避免决策函数在参数中临时声明“用户已经同意”。

## 收获

把“选择动作”和“根据事实出报告”分开之后，轨迹和交付结果可以分别核对。轨迹回答为什么调用这个工具，结果回答草稿到底有没有写上。上限也必须放在执行器里：即使换一个永远不结束的决策函数，调用次数仍然停住，并返回未完成。

可复现和“每一步都像远程模型”之间要做取舍。评分材料需要稳定的参数、摘要和后续动作，所以提交轨迹使用本地观察决策。远程适配器留在同一接口上，供有密钥时替换，但不拿它充当已经跑过的验收证据。

后来又补上一条确认边界：用户确认新时段，或原时段恢复可用并按原时间保存之后，旧的待确认草稿不能继续看起来有效。接替只改 `confirmation_status`，硬性发布时间留在原草稿上。保存失败时连这个状态也不能改，否则一次故障会让上一份待确认草稿消失。
