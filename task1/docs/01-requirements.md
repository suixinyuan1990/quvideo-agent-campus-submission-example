# 需求

## 用户

内容运营或审核同学。他们手里有待处理素材，需要知道能不能排期、有没有规则风险、要求的时间是否冲突，以及草稿有没有保存下来。他们不通过这个程序直接发布。

## 目标

对一条素材给出可核对的审核和排期结论：

- 审核状态
- 风险原因
- 建议时段
- 待确认项
- 草稿保存状态

结论必须能和工具返回对上。时段冲突时可以建议替代时间，但硬性发布时间只有在用户确认后才写入已承诺时段。

## 范围

纳入本程序：

- 读取 `data/materials.json` 中的单条素材。
- 用 `data/rules.json` 检查阻断级表述。
- 用 `data/slots.json` 查询要求时段和同一天的替代时段。
- 把排期建议写入草稿存储。
- 相同请求重复保存时复用同一份草稿。
- 工具故障、资料缺失、步数上限和调用次数上限都要给出明确状态。
- 新草稿成功保存后，把同一素材、同一内容版本、同一日期和要求时段上仍待确认的旧草稿标成 `superseded`。不改写硬性发布时间。保存失败不接替。

资料都在 `data/`，按验收场景手写，不从外部语料替换：

| 文件 | 内容 |
| --- | --- |
| `materials.json` | 待处理素材。M01 无风险且要求 18:00；M02 缺字段；M03 含三条阻断表述；M04 文案可排，保存故障单独注入 |
| `rules.json` | 阻断级表述：保证收益、零风险、立刻下单 |
| `slots.json` | 2026-11-12 的 18:00 被 SCH-1800 占用，19:00 空闲。其余验收日期只记录该素材要求的时段 |
| `tool_faults.json` | M04 的 `storage_unavailable`；M11 连续两次规则超时；M12 只超时一次 |
| `supplements.json` | 空对象，用来让 M02 的补查仍然失败 |

不纳入：

- 真实发布渠道、审批流账号和外部 CMS。
- 一次请求自动排完整个待处理队列。待处理标记在素材的 `queue_status`。
- 跨天日历、节假日和人工协商以外的排期优化。
- 用远程模型生成提交用的验收轨迹。远程模型只作为同一循环的可选适配器。

## 输入

请求 JSON 至少包含 `material_id`。可选字段：

| 字段 | 作用 |
| --- | --- |
| `confirmed_slot` | 用户同意改用的时段。空值表示尚未同意。 |
| `max_steps` | 决策次数上限，默认 8。 |
| `max_tool_calls` | 实际工具调用上限，默认 8。 |
| `repeat` | 只由运行入口处理，用来在同一个草稿库上连续提交。决策函数不读取它。 |

素材字段包括标题、正文、渠道、受众、日期、要求时段、是否硬性、内容版本和队列状态。M02 故意缺少标题、正文和受众。

## 成功标准

1. 无风险且时段可用时，保存一份未发布草稿，承诺时段等于用户要求。
2. 必要字段缺失时，先补查一次；仍然缺失就停止，不保存草稿。
3. 命中阻断级规则时，列出风险并停止，不查询替代时段来绕过规则。
4. 硬性时段被占用且用户未确认时，建议可用替代时段，草稿保持待确认，硬性要求保持原值。
5. 用户确认的时段可用时，才允许改写硬性时间；结果仍然不是发布。
6. 同一请求再保存一次，草稿数量保持 1，并返回 `duplicate`。
7. 存储失败时返回 `failed` 和错误码，草稿数量保持 0。
8. 规则工具没有给出可靠结果时，不把素材当成无风险。
9. 决策次数或工具次数达到上限时，`run_status` 为 `incomplete`，原因写明“任务未完成”。
10. 至少有两条真实轨迹在工具返回分叉后选择不同动作。提交中的分叉是示例 01 对 04，以及示例 07 对 11。

## 关键缺陷

以下任一情况都视为未达到要求：

- 出现发布动作，或把草稿状态写成已发布。
- 保存工具失败后仍报告保存成功。
- 没有用户确认就改写硬性发布时间。
- 相同请求生成多份草稿。
- 只按固定顺序调用工具，工具结果变化时下一步不变。
- 工具失败被执行器自动重试，决策记录里看不出是模型选择了补查。
